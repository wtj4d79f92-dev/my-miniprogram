# 旷行吖 · 户外组队小程序

按《产品设计文档.md》（PRD v1.0）实现的微信小程序，原生开发 + Skyline 渲染。**当前 `services/config.js` 为云开发模式（`useMock: false` / `useCloud: true`）**，数据与内容安全都走云函数；把 `useMock` 改回 `true` 即可切到本地 Mock 模式，无需后端就能跑通浏览、筛选、发布、报名、退出、我的活动、分享海报全流程（供演示与自动化校验使用）。

## 运行

1. 用微信开发者工具打开本项目根目录（AppID 已配置在 `project.config.json`）；
2. 直接编译即可，首页会自动生成 Mock 活动数据；
3. 需要真机预览时，工具菜单「预览」扫码即可。

## 数据层：Mock 与云开发

`services/config.js` 中 `useMock` 控制数据来源：

- `useMock: true`（演示模式）：数据由 `services/mock.js` 生成，操作结果写入本地缓存，缓存键与 PRD 5.3 一致（`aa_selected_city`、`square_pending_type`、`my_user`、`my_user_counter`、`my_published`、`my_joined`、`my_feedback`），另加 `mock_join_map`、`mock_status_map`、`mock_audit_map` 三个运行期缓存键，用于记录报名成员、关闭状态与关闭时间、本地审核结果。
- `useMock: false`：走云开发，客户端调用 `activity` 云函数，action 与 PRD 8.6 一致（`home / list / detail / create / update / join / quit / toggle / mine / user / login / updateUser / qrcode / feedback / report / deleteAccount`），审核相关调用走独立的 `admin` 云函数。

> Mock 模式下把当前登录用户视为审核人，本地也能把「发布 → 待审 → 驳回 → 修改重提 → 通过」整条链路跑通；云端真人权限见下方「活动审核」。

### 接入云开发（M5）

1. 在微信开发者工具中开通云开发，记录环境 ID；
2. 把 `services/config.js` 的 `useMock` 改为 `false`，`useCloud` 改为 `true`，填入 `cloudEnv`；
3. 在 `app.js` 的 `onLaunch` 中初始化：`wx.cloud.init({ env: config.cloudEnv, traceUser: true })`；
4. 创建集合 `activities`、`users`、`banners`、`feedback`，权限按 PRD 8.7 设置（用户举报与意见反馈都落在 `feedback`，用 `kind` 区分：`feedback` / `report`，同样只允许云函数读写）；
5. 新建 `cloudfunctions/activity` 云函数（Node.js），按 `services/api.js` 中 `cloudApi` 的 action 名实现路由，返回结构失败为 `{ code, message }`、成功为业务数据；
6. 在 `project.config.json` 中补充 `"cloudfunctionRoot": "cloudfunctions/"` 后部署云函数。

前端页面逻辑不依赖具体数据来源，切换开关即可，无需改动页面代码。

## 隐私与合规

发给审核与上线用的几条硬约束，后续改动不要退回去（`scripts/validate.js` 与 `scripts/cloud-validate.js` 里有对应断言）：

1. **接口不下发任何 openid**：活动相关输出统一走 `cloudfunctions/activity/lib/helper.js` 的 `publicActivity()` —— 它先按当前用户算好 `joined` / `isOrganizer`，再把 `joinedPeople` / `organizer` 换成只含昵称头像的快照。前端只认这两个布尔值（`pages/activity/detail/index.js`），不要再拿 `openid` 自己比对。自己的 openid 只出现在 `user` / `login` / `updateUser` 的返回里。
2. **昵称与活动文案一样要过内容安全**：昵称会展示在活动卡片与报名名单里，`updateUser`（含登录时前端带上来的 `profile.nickName`）和发布 / 编辑共用同一个 `checkText`，命中 `risky` 直接拒绝写库。
3. **举报入口**：活动详情页底部「举报该活动」（自己的活动不展示）→ `report` action → `feedback` 集合里 `kind: 'report'` 的记录，运营按 `kind` 区分反馈与举报；原因是固定候选，云端 `REPORT_REASONS`、`services/api.js`、`pages/activity/detail/index.js` 三处必须一致。举报只作为人工线索留存，不参与机审放行、不自动下架活动。
4. **协议可达**：登录页与「我的 → 用户服务协议 / 隐私政策」都能随时查看；《用户服务协议》第三条写明侵权投诉走「举报」入口，对应通知-删除通道。
5. **手机号只认微信授权 code**：`login` 只接受 `phoneCode`（服务端调 `phonenumber.getPhoneNumber` 兑换），不接受前端直接传入的号码；`updateUser` 不接受 `phone` 字段。默认昵称是「微信用户 + 用户编号」，**不用手机号（含 `138****8888` 这种掩码）**——昵称会展示在活动卡片与报名名单里；历史遗留的掩码昵称会在下次登录时就地纠正并同步已发布 / 已报名活动的快照。
6. **费用只做信息说明**：活动必须选 AA 制 / 非 AA 制，非 AA 制只填一段文字说明（≤60 字），不收集金额、不产生任何支付行为；**平台不收取、不代收、不托管任何活动费用，也不提供收款 / 代付 / 结算通道**，发布页与详情页固定展示这句口径，协议同步写明。
7. **入口与索引**：个人中心提供 `open-type="contact"` 客服入口（人工客服，纯后台配置，**不需要改代码、也不经过我们的服务器**）——后台「客服」页有「小程序客服」和「微信客服」两套能力，本项目用的 `open-type="contact"` 属于**小程序客服**：点左侧「查看」，添加客服人员并邀请其微信接受绑定，客服人员随后用微信官方客服小程序（后台提示的「小程序客服消息」，早期叫「客服小助手」）或后台网页端客服工作台回复用户；未添加客服人员时用户点进去会显示客服不在线。「消息服务器配置」只在走 API 收发时才需要填写。`sitemap.json` 对 `pages/admin/audit/index` 设 `disallow`，审核台不进微信搜索索引。
8. **发版包卫生**：`project.config.json` 的 `packOptions.ignore` 排除 `*.md` / `*.docx` / `scripts` / `.git` / `.DS_Store` / `.gitignore` / 工具私有配置，避免文档与本地文件被打进上传包。

## 注销账号

「我的」底部提供自助注销入口，两次确认后才真正执行（第一次说明后果，第二次是最终确认），注销不可撤销。注销时按「先内容、再报名、最后账号」的顺序清理，中途失败账号仍在，用户可以重新发起：

1. **我发布的活动**：连同 `cover` / `groupQrCode` / `miniQrCode` 三个云存储文件一起删除（Mock 模式清本地 `my_published` 与对应的状态、审核覆盖）；
2. **我在别人活动里的报名**：从 `joinedPeople` 里移除并同步 `joinedCount`；
3. **我提交的反馈与举报**：`feedback` 集合里该 openid 的记录删除（举报是 `kind: 'report'` 的同一集合记录）；
4. **账号本身**：`users` 里的记录删除。

`activity_audits` 里的审核日志保留：那是平台内容审核的留存记录，只含活动 id、标题与审核人信息，不含注销用户的昵称 / 头像 / 手机号。注销后同一个微信再次登录会重新注册为新账号（用户编号递增），历史数据不会回来。

## 活动关闭

发起人可以在「我的发布」或活动详情里关闭 / 重新打开自己的活动，关闭只影响新报名（已报名成员不受影响）。展示上是两条规则，Mock 与云函数同一套口径：

1. **只在广场保留关闭当天**：关闭时写 `closeTime`，广场列表只在 `closeTime` 落在当天时展示它，次日起不再出现；首页的热门 / 最新是推荐位，一律不展示已关闭的活动。详情、「我的活动」照旧可见，分享链接也不会失效；
2. **已关闭的活动沉底**：广场列表无论按最新发布还是最热门排序，都先排未关闭的活动，再排关闭当天可见的已关闭活动；云函数为此外拆成「未关闭」「已关闭」两条查询拼页，不需要为多字段排序加复合索引。

上线前关闭的活动没有 `closeTime`，按「早已关闭」处理（不再出现在广场），需要重新展示时让发起人重新打开一次即可。

## 活动展示期（发布后 7 天）

活动在首页与广场只展示 **发布后 7 天**，届满自动关闭。规则与实现都在 `utils/expire.js` 与 `cloudfunctions/activity/lib/expire.js`（两份内容一致，`scripts/validate.js` 会比对）：

1. **口径**：到期时间 = `createTime + 7 天`，不单独落一个到期字段 —— 只有一个来源，历史数据同样生效，不需要迁移；编辑重提不改 `createTime`，所以编辑不会重置展示期；
2. **为什么设展示期**：活动群二维码是微信群邀请二维码，有效期通常只有 7 天。展示期与二维码有效期对齐，避免「报名成功后扫到的是一张过期二维码」，广场也不会长期堆着没人跟进的活动；
3. **展示层过滤**：首页与广场的查询都带 `createTime > 现在 - 7 天`（`notExpiredWhere`），所以**即使定时任务没跑**，过期活动也不会露出来；
4. **对外状态归一**：`publicActivity` 把过期活动下发成 `status: closed` + `expired: true`，列表、详情、「我的发布」与报名守卫拿到的是同一套结论（卡片与详情页展示「已到期」，与发起人主动关闭区分开）；
5. **写操作守卫**：到期后不能报名（`ACTIVITY_EXPIRED`）、不能重新打开、不能编辑重提 —— 展示期按发布时间算，重开或改完也不会再展示，不如让用户重新发布；已报名的人仍可退出活动，不阻断用户清理自己的报名；
6. **详情与分享不失效**：过期活动点开详情照旧看得到，只是按钮变成「活动已到期」，集合时间、地点、导航仍可读；
7. **定时自动关闭**：`cloudfunctions/activity/config.json` 配了定时触发器（每小时整点），把 `status` 还是 `recruiting`、`createTime` 已过 7 天的活动改成 `closed`，`closeTime` 写**到期那一刻**而不是任务执行时刻 —— 否则广场「关闭当天仍展示」的规则会把一批过期活动重新捞出来。部署时要在开发者工具里对 `activity` 云函数「上传触发器」；没上传也只是库里的状态晚一点收敛，展示与守卫仍按第 3、4 条生效。

边界：发布满 7 天当天即到期（`>=`），6 天 23 小时仍算展示期内；待审中的活动到期同样会被关闭，不会一直挂在待审队列。

## 活动审核

用户提交的活动不会直接对外可见，需要审核通过后才展示。机审明确通过的由内容安全自动放行，只有机审拿不准的才需要人工过一遍（见下方「内容安全检测」）。状态字段与业务状态（招募中 / 已关闭）分离，互不覆盖：

| 字段 | 含义 | 取值 |
| --- | --- | --- |
| `auditStatus` | 审核状态 | `pending` 审核中 / `approved` 已通过 / `rejected` 未通过 |
| `auditRemark` | 驳回原因，发起人可见 | 审核人填写，最多 200 字 |
| `auditTime` / `auditBy` | 审核时间与审核人 | 人工审核由 admin 云函数写入，自动放行记为「内容安全检测」 |
| `submitTime` | 提交审核时间 | 待审队列按它倒序，编辑重提会重新排到最前 |

规则：

1. 发布、编辑后一律先回到 `pending`：机审全过时立刻转为 `approved`，机审疑似 / 异常时才留在待审队列；编辑已通过的活动也会重新送审（否则先发合规内容过审、再改成违规内容就能绕过审核）；
2. 首页、广场、列表的查询都带审核条件，`pending` / `rejected` 只有发起人自己能看到（详情页会给发起人展示审核提示条）；
3. 审核中 / 未通过的活动不能报名、不能关闭或打开；
4. 没有 `auditStatus` 字段的历史数据按「已通过」处理（查询用 `nin` 而不是 `eq`），所以**上线审核能力不会让存量活动从列表里消失**；
5. 驳回后发起人在「我的发布」里能看到原因，并可直接进入发布页修改重提。

对发起人只说「审核中」：机审还是人工复核属于平台内部流程，发布页、活动详情与「我的发布」都不区分（文案见 `pages/activity/publish/index.wxml`、`pages/activity/detail/index.wxml`、`pages/user/activity-list/index.wxml`）。发起人能看到的确定性结论只有两种：审核中，或未通过 + 原因。

### 封面 / 群二维码的云存储地址

封面与群二维码以 `cloud://` 文件 ID 落库，而审核人通常是另一个微信号：客户端直接渲染别人的云存储文件，能不能加载完全取决于云存储的权限设置 / 安全规则，被限制成「仅创建者可读」时审核台只会看到「封面加载失败」。因此：

1. `admin` 云函数的列表与详情用管理员身份把 `cloud://` 批量换成 `https` 临时链接（响应里的 `media: { [fileID]: { url, ok, reason } }`），审核台优先渲染这些地址，图片位置只作为兜底；
2. 首页 / 广场 / 我的活动 / 活动详情由 `activity` 云函数下发同样的临时链接（活动上的 `coverUrl` / `qrUrl`），活动卡片与详情页优先渲染它们，两者都保留原始 `cover` / `groupQrCode` 以便重取；
3. 临时链接默认 2 小时过期，图片加载失败时前端按 fileID 调 `media` 接口重取一次，仍失败才退回默认海报 / 占位图；
4. 服务端也取不到时（文件被删、上传到了别的环境、权限过严），审核台会直接说清原因并把 fileID 露出来，而不是留一块空白灰块；
5. `activity` 云函数在发布 / 编辑写库前会用同样的方式校验一次：明确「文件不存在」就返回 `UPLOAD_FAILED` 让用户重新上传，接口本身异常则放行（不能因为云存储抖动让用户发不出活动）。

> 云开发控制台「存储 → 权限设置」正常应是「所有用户可读，仅创建者可读写」，但客户端渲染仍可能被安全规则、跨环境文件 ID 影响，所以列表接口不再依赖客户端直读云存储。仍走客户端 `wx.cloud.downloadFile` 的是分享海报里的群二维码与小程序码（画布需要本地文件），若这两张图偶发缺失，可用同一条 `media` 接口替换来源。

### 部署步骤

1. 部署 `cloudfunctions/admin`（审核台）、`cloudfunctions/activity`（业务改动）两个云函数；`activity` 的 `config.json` 里还带一个「到期自动关闭」的定时触发器（见「活动展示期」），上传时选「上传触发器」一并生效；
2. 给自己开通审核权限，二选一：
   - 在 `admin` 云函数的环境变量里配置 `ADMIN_OPENIDS=<你的 openid>`（首位管理员用这个，openid 可以在审核页的「没有审核权限」提示里直接复制）；
   - 新建 `admins` 集合，写入 `{ "openid": "...", "name": "运营昵称" }`，日常增删审核人只改这里；
3. 可选：在审核台底部点「补齐全量审核状态」，给历史活动写入显式的 `approved`（幂等，可重复执行，不迁移也不影响展示）；
4. 重新编译小程序，登录后「我的」页会出现「活动审核」入口（仅审核人可见）。

配套集合：`activity_audits` 记录每次审核的动作、前后状态、原因、审核人与时间（集合不存在时会自动跳过写日志，不阻塞审核）。集合权限建议设为「仅创建者可读写」或「所有用户不可读写」，只通过云函数访问。

## 分享入口（首页 / 活动详情）

微信右上角菜单里的「发送给朋友」「分享到朋友圈」是**按页面**的分享回调决定可用性的：页面没实现 `onShareAppMessage` / `onShareTimeline`，这两个按钮就是灰的（文案是「当前页面不可转发 / 当前页面不可分享」）。首页此前只有详情页实现了回调，所以整个小程序没有对外的分享入口。

| 入口 | 分享回调 | 卡片内容 |
| --- | --- | --- |
| 首页 | `onShareAppMessage` / `onShareTimeline` | 标题「旷行吖 · 同城找搭子，一起出发」，路径 `/pages/home/home`，好友卡片图 `assets/share-home.png`、朋友圈卡片图 `assets/logo.png` |
| 活动详情 | 同上 | 标题带活动名「一起去组队」，路径带活动 id，图用封面（云端换好的 https 临时链接） |

首页卡片的图用代码包里的品牌图，不依赖微信对页面截图的结果——首屏还没加载完就转发时，截图可能是空白的。两个入口的卡片比例不同，所以备了两张：发送给朋友是 5:4，用 `assets/share-home.png`（500×400，按 logo 的包围盒重新排过一次版，不会把 logo 裁掉）；分享到朋友圈是 1:1，直接复用 `assets/logo.png`（480×480）。卡片标题与路径是纯文本，和登录态、接口无关，因此好友点开、未登录时也能正常落地。

首页是 tabBar 页面，被分享到朋友圈后同样会进「单页模式」（见下一节）：页面配置了 `singlePage.navigationBarFit: "squeezed"`，单页模式下不渲染自定义导航栏与「发布」悬浮按钮，搜索 / 玩法 / 活动卡片 / 定位这些需要跳转或授权的入口一律静默（微信在单页模式下禁用页面跳转，硬跳只会弹「请前往小程序使用完整服务」），顶部如实说明「仅展示活动信息，搜索、报名需在小程序内操作」。朋友圈里打开首页同样要在云开发控制台开「允许未登录访问」，否则首页只能落到空列表。

广场 / 我的两个 tab 页面还没有实现分享回调，微信里同样是灰的；要开的话按首页这套（回调 + 单页模式适配）补齐即可。

## 分享到朋友圈（单页模式）

用户在朋友圈点开分享卡片时，微信**不会**打开完整小程序，而是进入「单页模式」（场景值 1154）：顶部导航栏与底部「前往小程序」操作栏由微信渲染，页面自身**没有登录态**，跳转、页内分享、报名这些交互也被禁用。官方限制见[分享到朋友圈](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/share-timeline.html)。

上线前必须在云开发控制台做两件事，否则**审核通过、正常招募中的活动在朋友圈里也会显示成「活动不存在或已下架」**——未登录的云函数调用会被安全规则直接拦下，前端一条数据都拿不到：

1. 云控制台 → 设置 → 权限设置：为云环境开启「允许未登录访问」；
2. 开启后云函数 / 数据库 / 文件存储都必须改用安全规则（未登录访问时规则里的 `auth` 为 `null`，见[未登录模式](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloud/basis/identityless)）：
   - `activity` 云函数：`{ "activity": { "invoke": true }, "*": { "invoke": "auth != null" } }` —— 只放开活动接口，`admin` / `seed` / `contentCheck` 仍然要求登录态；需要身份的 `create` / `update` / `join` / `quit` / `toggle` / `mine` / `report` / `deleteAccount` 在云函数内部另有 `openid` 守卫，未登录一律返回 `UNAUTHORIZED`（`feedback` 是唯一例外：意见反馈本来就允许未登录提交，记录里的昵称会写成「未登录用户」）；
   - 数据库：`{ "read": false, "write": false }` —— 客户端从不直连数据库，读写都走云函数（服务端不受安全规则限制）；
   - 文件存储：`{ "read": true, "write": "resource.openid == auth.openid" }` —— 与现状「所有用户可读，仅创建者可读写」等价，分享海报里的群二维码要由 C 端直接下载。

没做这一步时的现象可以在开发者工具里稳定复现：把编译场景值设成 1154（模拟朋友圈打开）后，`wx.cloud.callFunction` 会返回
`errCode: -501023 permission denied | errMsg: Unauthenticated access is denied`（HTTP 500），页面拿不到任何数据，只能落到兜底态。

页面侧（`pages/activity/detail/index.js`）已按官方要求做了适配：

1. 按场景值 1154 识别单页模式，并且不把场景值当成活动 id（`options.scene` 既是小程序码里的活动 id，也可能是启动场景值）；
2. 详情页 JSON 配 `singlePage.navigationBarFit: "squeezed"` —— 自定义导航栏页面在单页模式下默认是 `float`，微信导航栏会压住页面内容；
3. 单页模式下不渲染被禁用的 `navigation-bar`，隐藏分享 / 举报 / 返回入口，主按钮降级为「浏览模式不可报名」（不做「点击前往小程序」这类诱导），活动信息照常完整展示；
4. 接口失败与「活动不存在」分开：失败显示可重试的「加载失败」，不再谎报下架。`services/api.js` 的 `callCloud` 把原始错误挂在 `err.raw`（`errCode` / `errMsg`）上，便于区分网络问题与安全规则拦截。

`activity` 云函数已经做到「没有 openid 也能查公开活动」：`detail` / `home` / `list` 只用文档数据，未登录时 `publicActivity(doc, '')` 给出的 `joined` / `isOrganizer` 都是 `false`。

## 机审：内容安全检测 + 群二维码识别

审核解决「人来看」，机审解决「机器先筛」：机器拦下明确违规的、放行明确合规的，只有机器拿不准的才进人工队列。三类检测的实现路径不同：

| 检测对象 | 接口 | 特点 | 接入点 |
| --- | --- | --- | --- |
| 标题 / 地点 / 活动介绍 | `security.msgSecCheck` | 同步返回结论 | `activity` 云函数的 `create` / `update` |
| 封面 / 群二维码 | `security.mediaCheckAsync` | 异步，只返回 `trace_id`，结论靠消息推送回调 | 同上发起，`contentCheck` 云函数接收 |
| 群二维码内容 | `img.scanQRCode`（云调用） | 同步，只认微信群邀请链接 | 同上：`activity` 云函数把 `cloud://` 换成 https 临时链接后送识别 |

结论的处理方式：

| 机器结论 | 文本 | 图片 |
| --- | --- | --- |
| `risky` | 直接拦下：返回 `CONTENT_RISKY`，**不写库**，用户在发布页看到提示后修改重发 | 直接驳回：审核中的标记未通过；**已上线的立即下架**，发起人看到「图片经内容安全检测判定违规」 |
| `review` | 留在待审队列给人工，同时打 `machineReview` 标记，审核台提示「机器需复核」 | 同上 |
| `pass` | 进待审队列等图片结论，不单独放行 | 写回 `pass`，清除「图片检测中」；**所有送检项都通过时活动自动放行** |
| 没有结论（`failed`） | 接口超时 / 报错 / 响应里没有结论：留待审队列交给人工，审核台显示「文本检测失败（转人工）」；图片结论回来时会补检一次文本（见下） | 推送里带错误码或没有 `result`：记 `failed`，留待审队列交给人工，审核台显示「未出结论（转人工）」 |

群二维码识别（`machineCheck.qrcode`）只看一件事：**这张图扫出来是不是微信群邀请链接**（`https://weixin.qq.com/g/xxxxx`）。结论分四种：识别不出群码的两种直接驳回，只有拿不到结论的异常才转人工：

| 结论 | 触发条件 | 处理 |
| --- | --- | --- |
| `ok` | 识别到微信群邀请链接 | 记录链接内容，作为自动放行的必要条件 |
| `not-qrcode` | 图里没识别到任何码（传了风景照、截图糊到认不出等） | **直接驳回**，`auditRemark` 写「活动二维码上传有误，请重新上传微信群二维码」，不进人工队列 |
| `not-group` | 识别到码了，但不是群邀请链接（收款码、商品码、别的平台群码等） | 同上：直接驳回，审核台仍能看到识别到的内容 |
| `failed` | 临时链接取不到 / 接口报错 / 超过预算 | 转人工，**不拦下发布**（与内容安全同样的降级原则） |

驳回规则见 `cloudfunctions/activity/index.js` 的 `qrRejectPatch`（判定在 `lib/contentCheck.js` 的 `isQrRejected`，前端 Mock 用同名的 `mockQrReject`）。发起人在详情页与「我的发布」看到「未通过原因：活动二维码上传有误，请重新上传微信群二维码」，改好二维码重新提交即重新走一遍检测，并留一条 `action: auto-reject` 的审核日志。识别接口异常（`failed`）**不**沿用这条规则：没有结论不能驳回用户，仍留在待审队列交给人工。

活动文档会落 `machineCheck: { text, images, qrcode, checkedAt }`，以及便于查询的 `machineReview` / `machinePending` 标记，审核台详情页直接展示文本结论、每张图的检测结果与二维码识别结论。

### 机审自动放行

规则只有一条：**所有送检项都明确通过，才不等人工直接放行**，写 `auditStatus: approved`、`auditBy: 内容安全检测`，并留一条 `action: auto-approve` 的审核日志。也就是文本 `pass`、群二维码识别出微信群邀请链接、封面与群二维码的图片内容安全全部出结论且都是 `pass`。只要有一项是 `review`、识别/送检失败、或结论还没回来，就留在待审队列交给人工。判定逻辑放在 `cloudfunctions/activity/lib/autoAudit.js` 与 `cloudfunctions/contentCheck/lib/autoAudit.js`（两份内容一致，分别负责发布当刻与图片回调时的判定）。

写库那一刻的优先级是：`qrRejectPatch`（二维码明确不是微信群码 → 直接驳回）> `autoAuditPatch`（机审全过 → 直接放行）> `auditPatch`（其余 → 待审）。被二维码驳回的活动 `auditStatus` 已是 `rejected`，图片结论回来后 `contentCheck` 的自动放行只处理 `pending` 的活动，不会把驳回结论覆盖掉。

两个实现上的注意点：

1. **自动放行是异步发生的**：封面 / 群二维码走 `mediaCheckAsync`，发布时只有 `trace_id`，所以活动发布后仍是「审核中」，通常几秒后拿到全部图片结论才自动上架，不是点发布那一刻就可见；
2. **不完整的结论不算通过**：某张图没能送检（临时链接生成失败、接口报错）时，`images` 里就少了这一条，判定会用「该送检的图片数」和「已有结论的图片数」比对，宁可转人工也不放行。

**「机审看着全绿，却还是进了人工审核」不会再出现**。以前有两种情况会让运营看不懂：发布当刻文本检测超时 / 接口异常只留下 `text.failed` 标记，接口推送里没带结论时图片又会被当成 `pass`，而审核台只按 `suggest` 显示，于是三行全是「机器通过」、活动却卡在待审队列。现在：

- 审核台区分「机器通过」与「没结论」：文本 `failed` 显示「文本检测失败（转人工）」，图片没有结论显示「未出结论（转人工）」，该送检的云存储图片没送出去会标「图片未送检」，待审卡片上同样有这几个标记；
- 图片结论回来那一次回调会给「当时没拿到结论」的文本**补检一次**（`cloudfunctions/contentCheck/lib/textCheck.js` 与 `cloudfunctions/activity/lib/textCheck.js` 内容一致），补到结论就照常自动放行，补不到就继续交给人工，并写一条 `action: text-recheck` 的审核日志。

没有可送检图片时（封面 / 二维码都不是云存储文件）不存在这个等待，发布当刻即按文本结论与二维码识别结论决定。

### 关键取舍

**检测接口失败一律降级为纯人工审核**（接口未开通、超出额度、openid 不满足条件、云存储临时链接生成失败等），只打 `console.error` 并在 `machineCheck` 里留下失败标记：既不因为机审自身出问题而让用户发不出活动，也不会因为检测不可信就把内容自动放上线。

图片送检与二维码识别都先用 `cloud.getTempFileURL` 把 `cloud://` 文件 ID 换成临时 http 链接——`mediaCheckAsync` 与 `img.scanQRCode` 都只接受可访问的 URL，不接受云存储文件 ID。

### 部署步骤

1. 机审自动放行改了两个云函数：**发布当刻的判定在 `cloudfunctions/activity`，图片结论回来后的判定在 `cloudfunctions/contentCheck`，两个都要重新部署才是完整行为**（只部署一个时，另一侧的判定还是旧逻辑：图片结论写回了，放行判定却没跑，审核台看着「全绿」但活动仍在待审队列）；
2. `cloudfunctions/activity/config.json` 已声明 `security.msgSecCheck`、`security.mediaCheckAsync`、`img.scanQRCode` 三个云调用权限，文本补检让 `cloudfunctions/contentCheck/config.json` 也声明了 `security.msgSecCheck`（`scripts/validate.js` 会检查声明与代码是否一致，漏了会报错），无需再改；
3. 在 mp 后台「开发管理 → 接口设置」开通内容安全接口；二维码识别（`img.scanQRCode`）若未开通或调用报错，识别结论是 `failed`（没有结论），发布照常成功、活动留在待审队列转人工（不会把用户卡在发布页，也不会被误驳回）；
4. 到 mp 后台「开发管理 → 消息推送」选择**云开发消息推送**并指向 `contentCheck` 云函数——图片结论只能通过这条链路回来，不配的话活动永远拿不到图片结论，也就是每条发布都会退化成人工审核（这一页的 URL / Token / EncodingAESKey 都不用填）；
5. 消息推送**全小程序只能配一个接收方**，以后要接客服消息等其他事件，在 `contentCheck` 里按 `MsgType` / `Event` 分发。
6. 建议给 `activities` 集合加一个 `machineCheck.images.traceId` 索引，回调查找走的是这个字段（数据量小的时候不加也能跑）。

时序上有个已知窗口：图片结论回来之前活动可能已被人工放行，此时若判定违规会自动下架（复用同一套 `auditStatus: rejected`，发起人能看到原因）。要彻底避免，可在审核台对 `machinePending` 的活动暂缓通过。

Mock 模式下用关键词模拟：「违规 / 赌博 / 代刷 / 外挂」会被拦下，「疑似 / 兼职」会标记为需复核；群二维码识别按文件名模拟 —— 文件名含 `noqrcode` 表示图里没识别到码，含 `notgroup` 表示识别到的不是微信群邀请链接，其余一律视为识别到微信群邀请码，方便本地验证三种结论与审核台展示。

## 提审演示数据（造数据）

提审时审核员看到的是**线上云数据库里的真实数据**，`activities` 集合为空时首页与广场只有空态，很容易被判成「功能不完整」。演示数据放在 `cloudfunctions/seed`，与真实用户数据隔离（`isDemo: true` + `demo_act_*` 的 `_id`），清理时只删这一批。

数据源只有一处：`cloudfunctions/seed/lib/data.js`（32 条活动，覆盖 12 个城市 / 全部 10 种活动类型 / 未来 7 天，每天不少于 2 条、7 个星期几都有）。字段口径与发布接口 `normalizeForm` / `create` 对齐，`scripts/validate.js` 会逐项对账（字段清单、类型字典、城市 key、7 天展示期、报名名额、字段长度、AA / 非 AA 费用说明）。几条硬约束：

- 全部 `auditStatus: approved` —— 审核中 / 未通过的活动只有发起人看得到，造了也白造；
- `createTime` 为当前时间、`startTime` 在未来 —— 展示期是「发布后 7 天」（见「活动展示期」），一导入就过期的数据等于空态；
- 每条活动都留 2 个以上空位，审核员点进任意一条都能走完报名流程；
- 报名人数与报名名单一致（人数不是随手写的数字，名单里真的有那么多成员）。

### 方式一：seed 云函数（推荐，可重复执行、可续期）

1. 部署 `cloudfunctions/seed`；
2. 云函数环境变量配置 `SEED_TOKEN=<一串只有你知道的口令>`（没配就直接拒绝调用，避免被外部随便触发）；想让审核期间自动续期再加 `SEED_REFRESH=1`；
3. 云开发控制台 → 云函数 → `seed` → 云端测试，依次可用：
   - `{ "action": "seed", "token": "<SEED_TOKEN>" }`：写入 / 覆盖全部演示活动，时间字段重置为当前时间；
   - `{ "action": "refresh", "token": "<SEED_TOKEN>" }`：只把时间字段往后推（内容、封面、群二维码不变），审核拖久了跑一次即可；`SEED_REFRESH=1` 时每天的定时触发器（04:07）会自动跑它；
   - `{ "action": "status", "token": "<SEED_TOKEN>" }`：看演示数据与真实数据的条数；
   - `{ "action": "clear", "token": "<SEED_TOKEN>", "confirm": "DELETE_DEMO" }`：删除全部演示活动。
4. 一次性写入 32 条，云函数默认超时时间可能不够，控制台里把 `seed` 的超时调到 20 秒；
5. 想在演示活动上带封面 / 群二维码：先把图片传到云存储，调用时带上 `"cover": "cloud://..."` 与 `"qr": "cloud://..."`。

不勾「上传触发器」也能正常手动执行（`config.json` 里那条定时触发器只负责自动续期）。

### 方式二：云开发控制台导入（不部署云函数）

```bash
node scripts/seed-data.js                                        # 生成 scripts/seed/activities.json
node scripts/seed-data.js --qr=cloud://xxx --cover=cloud://xxx    # 可选：带上群二维码 / 封面
```

打开云开发控制台 → 数据库 → `activities` → 导入 → 选 `scripts/seed/activities.json`（JSON Lines，一行一条）。导入对话框有冲突处理选项时选「覆盖」；没有该选项就先在控制台删掉 `demo_act_*` 再导入。导入的是静态时间戳，**建议提审前一两天再导出导入**，拖久了重新生成导入一次。

### 提审前后的注意点

1. **别太早导入**：活动发布满 7 天自动关闭并从首页 / 广场消失（`createTime + 7 天`，见「活动展示期」），提审前一两天导入最稳，审核期间用 `refresh` 续期；
2. **审核通过后清理**：跑 `clear`，或在控制台删掉 `demo_act_*`；也可以留下几条作为冷启动内容；
3. **群二维码**：演示数据默认不带二维码（详情页不出现「查看二维码」入口）。要让审核员看到「报名成功 → 扫码入群」这一段，上传一张真实的微信群二维码并把 fileID 传给 `seed` / 导出脚本；
4. **审核员自己发布时走真实机审**：上传的群二维码必须是微信群邀请二维码，否则会被识别成「二维码上传有误」直接驳回（见「机审」一节），建议自己也准备一张备用；
5. **演示用户不是真实账号**：演示活动的发起人 / 报名成员是 `demo_u_*` 的假 openid，不会出现在任何真实用户的「我的发布」「我参与的」里，也不会因为真实用户改昵称而被同步。

## 校验

```bash
node scripts/validate.js
node scripts/cloud-validate.js
```

会检查：页面与组件的文件完整性、`usingComponents` 引用是否可解析、JSON 是否合法、JS 是否可通过语法解析，并跑一遍 Mock 业务链路（首页 → 广场筛选 → 详情 → 发布 → 报名 → 我的活动 → 关闭活动 → 退出 → 反馈 → 机审自动放行 → 注销账号）。

`scripts/cloud-validate.js` 用内存数据库替代 `wx-server-sdk`，直接调用四个云函数（`activity` / `admin` / `contentCheck` / `seed`）的入口，覆盖：审核前后在首页 / 广场 / 详情的可见性、发布与编辑重提、报名与关闭的审核守卫、已关闭活动的当天可见与沉底排序（含跨页、城市筛选叠加、次日消失、重新打开归零）、审核人权限（含越权调用被拒）、待审列表与统计、驳回原因校验、审核日志、历史数据迁移，以及机审（文本违规拦截不写库、疑似标记复核、图片异步回调写回、图片违规自动驳回与下架、机审全过自动放行、二维码没识别出微信群码时直接驳回且不进待审队列、被驳回后图片全通过也不放行、部分图片没结论 / 文本质疑 / 识别接口异常转人工、人工驳回后不被机审放行、接口异常降级）。机审接口在测试里是桩，通过行为开关切换文本与图片的 pass / review / risky / 调用失败、响应里不带结论、仅首张图送检失败，以及二维码的识别到群链接 / 没识别到码 / 不是群链接 / 只有一维码 / 调用失败；「没结论」这条线单独覆盖：文本降级 → 图片结论回来后补检文本 → 补到结论自动放行（日志写明补检）、补检仍失败继续转人工（记 `text-recheck`）、图片推送没结论时不写 `pass` 也不放行（记 `image-failed`）、旧版推送只带 `isrisky` 仍按结论处理。演示数据那组还会真的走一遍首页 / 广场 / 详情 / 报名与清理，确认造出来的数据审核员看得到、`refresh` 能把 7 天展示期往后推、清理时不动真实活动。它是纯本地运行，不依赖云环境，也不改动云端数据。

## 已知限制（与 PRD 12.4 一致）

- Mock 模式下封面 / 群二维码为本地临时路径，仅当前会话有效；
- 发布时间精度只到日期，不选具体时刻；
- 城市归属依赖集合地点文本匹配，个别命名可能误判；地址里认不出城市（如手输「双流区润和路附近」）时按发布者当前城市兜底，本次改动之前发布的同类活动需要编辑重提一次才会重新归属；
- 地图选点发布的活动带着坐标，点「导航」直接开地图；只有地址文本的老活动（含本次改动前发布的）要先把地址解析成坐标，这一步依赖腾讯位置服务 key（`services/config.js` 的 `mapKey`）与 `apis.map.qq.com` 的 request 合法域名，未配置时应用会请用户在地图上点一次位置再导航；
- 活动管理支持关闭 / 打开与编辑重提，暂不支持删除；
- 审核结果暂未通过订阅消息通知发起人（订阅消息需用户在发布时授权「审核结果通知」，属于独立的一步）；
- 机审已接入：文本与图片内容安全、群二维码识别都明确通过才自动放行；群二维码没识别出微信群邀请链接时直接驳回（原因「活动二维码上传有误，请重新上传微信群二维码」），其余（`review`、检测异常、结论没回来）转人工，且审核台会把「文本检测失败 / 图片未出结论 / 图片未送检」这些转人工的原因标出来；图片结论依赖消息推送回调，未配置接收方时发布一律退化为人工审核（发布当刻文本检测没结论的活动，会在图片结论回来时补检一次文本）；
- 群二维码只认微信群邀请链接：企业微信群码、QQ 群码、以及带水印到识别不出的截图都会被判为「不是微信群邀请二维码」而直接驳回（需要放宽时改 `cloudfunctions/activity/lib/contentCheck.js` 的 `GROUP_LINK_PATTERN`）；
- 分享海报里的小程序码由 `wxacode.getUnlimited` 生成，`scene` 存活动 id、`page` 指向活动详情。小程序**未发布**时按 `envVersion: release` 生成会失败（海报退化成「小程序码」占位），首审 / 内测阶段可在 `activity` 云函数的环境变量里设 `WXACODE_ENV=trial`，上线后删掉即恢复正式版；详情页 `onLoad` 同时认 `id`（分享卡片 / 页面跳转）与 `scene`（小程序码，需 `decodeURIComponent`），两条入口都能落到对应活动；
- 协议主体已按运营方提供的文档填写为「旷行吖科技（成都）有限公司」；《活动发布免责协议》《活动风险告知与免责协议》正文与根目录同名 .docx 逐段一致，管辖法院等条款仍待法务确认。

另外几处按 PRD 建议做了增强：自研日历禁止选择早于今天的日期；集合时间后移时自动顺延返程时间；地图选点把「展示值」和「匹配值」拆开——`location` 存「选点地址的省 + 市 + 地点名」（如「四川省成都市 华府大道地铁站」，表单、广场、详情、海报都显示它；地点名本身已带省市时不重复加），完整地址另存 `locationAddress` 且不出现在任何展示位，只用于城市归属与地址关键词检索，所以活动既不会「选 A 显示 B」，也不会因为地点名没带省市而归错城市；地点文本带上省市后，只有地址文本的老活动点「导航」时地理编码的命中率也更高。

集合地点缺省市时还有两层兜底：发布页在输入框下方直接提示「活动将按当前城市展示」，服务端在城市匹配不出时用这个当前城市兜底落库，避免活动城市为空、按城市筛选永远看不到；点地点调起导航时同一条地址会带上城市再解析一次，仍解析不出坐标就请用户在地图上点一次，选中后立刻用该坐标调起地图软件，不再只留一个「无法自动定位」的弹窗。
